# 1.0.1 — fixes from the 1.0.0 live smokes: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the seven things the 2026-10-15 live smokes proved broken in 1.0.0 work — task due dates, deal updates, organization responsibles, board field creation, deal tags, deal sorting and the error text the API already sends — and release the result as 1.0.1.

**Architecture:** No new tools, no new operations. Each fix lands where the live finding sits: the HTTP client learns the API's three error shapes; the task tools send the date keys the API honours; the custom-field client reads the second envelope the board route uses; the deal tool updates through `PUT` and the link routes because `PATCH` ignores most of its body; the organization tools send the one key that works. Every change is backed by a live observation recorded in `docs/FOLLOWUPS.md` #21–#25, and the two smoke scripts re-run on the fixed build before the tag.

**Tech Stack:** TypeScript 5 (NodeNext ESM, `.js` import suffixes), Node ≥ 18, `@modelcontextprotocol/sdk` ^1.0, `zod` ^3.23, `chrono-node` ^2.10, `vitest` 2, GitHub Actions (tag-triggered publish).

**Spec:** `docs/FOLLOWUPS.md` entries **#21 (b, f, k)**, **#23 (a)**, **#24 (f, h, k, n, "also found")** and the fix list in **#25** — every line there is a live observation of 2026-10-15, not a spec reading. The design spec (`docs/superpowers/specs/2026-10-02-weeek-full-api-coverage-design.md`) still binds §3.4 (naming, destructive gates) and §4 (name resolution).

## Facts this plan rests on (all verified against the live API on 2026-10-15)

- **Task dates.** `POST /tm/tasks` sets the due date from `day` in `d.m.Y` (`"20.11.2026"`); an ISO value answers 422 `The day does not match the format d.m.Y.`. `PUT /tm/tasks/{id}` sets it from `dueDate` in `Y-m-d`; `dueDate: null` clears. `dayFrom`, which the code has sent since 0.1, is ignored on both routes. `startDate` (`Y-m-d`) on `PUT` must travel with `dueDate` in the same body (422 `The due date field is required when start date is present.` otherwise) and this workspace then answered `200 {"success":false,"reason":"limit"}` without applying it — a plan limit. On create `startDate` is dropped silently next to `dueDate` and refused next to `day`, so `start` stays an update-only parameter.
- **Error bodies.** A 422 carries `{ success: false, errors: { dueDate: ["…"], day: ["…"] } }` and no `message`; a refused 200 carries `{ success: false, reason: "limit" }`. The client reported both as the bare `WEEEK API error`.
- **Board custom fields.** `POST /tm/boards/{id}/custom-fields` answers `{ success, data: { id, name, type } }`, not `{ customField }` as the spec says; the global, project and funnel routes answer `{ customField }`. A board's fields are read off a page of its tasks, so a cached empty board stays empty for 60 s after a task is moved onto it.
- **Deals.** `PATCH /crm/deals/{id}` honours only `title`, `amount` and `winStatus`; it ignores `description`, `assignees` (a list or `[]`), `organizations`, `contacts`, `tags` and `customFields` (a value or null). `PUT /crm/deals/{id}` honours `title`, `amount`, `winStatus` and `customFields` (null clears), accepts any subset (even `{}`), and **keeps every field it is not sent**. `description` is applied only on create. The add/remove routes for assignees, organizations, contacts and tags work. A deal's `tags` come back as `{ id, title, color }` objects, while organizations and contacts send plain ids. `GET /crm/statuses/{id}/deals?sort=amount` answers 500; `title`, `commented`, `createdAt`, `updatedAt` answer 200.
- **Organizations.** `responsibles: [uuid]` is ignored on `POST` and `PUT`; `responsibleId: uuid` is honoured on both and `responsibleId: null` clears; a `PUT` without the key keeps the current responsible.
- **Projects.** `GET /tm/projects` omits archived projects, so a name cannot resolve one; a tag's colour is hex (`#02BCD4`), and the project colour route takes the same.

```ts
/**
 * The API reports a refusal three ways (verified live 2026-10-15, FOLLOWUPS 24 "also found"):
 * a `message`; a per-field `errors` map on a 422, with no message at all
 * (`{ dueDate: ["The due date field is required when start date is present."] }`); and a 200
 * whose body says `success: false` with a `reason` (`"limit"` when the workspace's plan lacks
 * the feature). All three are errors to the caller, and this is the one place they are read.
 */
export function describeApiError(json: Record<string, unknown>): string {
  const parts: string[] = [];
  if (typeof json.message === "string" && json.message !== "") parts.push(json.message);
  if (typeof json.errors === "object" && json.errors !== null) {
    for (const [field, reasons] of Object.entries(json.errors as Record<string, unknown>)) {
      parts.push(`${field}: ${Array.isArray(reasons) ? reasons.map(String).join(" ") : String(reasons)}`);
    }
  }
  if (typeof json.reason === "string" && json.reason !== "") parts.push(`WEEEK refused the request (reason: ${json.reason})`);
  return parts.length > 0 ? parts.join("; ") : "WEEEK API error";
}
```

```ts
/** A `Y-m-d` day as POST /tm/tasks wants it: `d.m.Y` (`2026-11-20` → `20.11.2026`, FOLLOWUPS 21 b). */
export function formatDayMonthYear(isoDay: string): string {
  const match = /^(\d{4})-(\d{2})-(\d{2})$/.exec(isoDay);
  if (!match) throw new Error(`expected a Y-m-d day, got "${isoDay}"`);
  const [, year, month, day] = match;
  return `${day}.${month}.${year}`;
}
```

```ts
/** One list of a deal brought to `wanted` with the add/remove routes — PATCH ignores the lists (FOLLOWUPS 24 f). Undefined means "leave it". */
async function syncLinks<Id>({ current, wanted, add, remove }: LinkSync<Id>): Promise<void> {
  if (wanted === undefined) return;
  const have = new Set(current);
  const want = new Set(wanted);
  for (const id of wanted) if (!have.has(id)) await add(id);
  for (const id of current) if (!want.has(id)) await remove(id);
}
```
