# Follow-ups (deferred from the v0.1 whole-branch review)

None of these block v0.1; the create-by-name path is verified sound and token handling has no leak. Ordered roughly by value.

1. **`config.ts` empty-string timeout** — `WEEEK_TIMEOUT_MS=""` coerces to `0` and fails `.positive()` instead of using the `30000` default. Add an empty-string→undefined pre-transform. (Fails loudly at startup; low blast radius — README never asks users to set it.)
2. **`NameCache` request-coalescing** — two concurrent cold `get()` calls for the same key both run `load()`. Cache the in-flight promise. Wasteful, not incorrect.
3. **`cache.ts` `get<T>` unchecked cast** — safe today because each key prefix (`projects`/`members`/`columns:`/`board-columns:`) maps to one type; nothing enforces it. Consider a typed cache-key registry.
4. **`weeek_create_tasks` bulk handler vs `reply.ts` duplicate `ResolutionError`→candidates logic** — two implementations of the same rule (the bulk handler in `src/tools/tasks.ts` and `errorReply` in `src/tools/reply.ts`). Extract one helper so a future tweak (e.g. cap candidate count) touches one place.

6. **`TasksApi.move` is two non-atomic POSTs** (`/board` then `/board-column`). If the second fails, the task is on the new board with its old column, surfaced only as a generic error. Likely a WEEEK API limitation; track, don't block.

15. **Reassigning an existing task is not possible via the public API** — verified live: `PUT /tm/tasks/{id}` with `assignees`, `userId`, or an empty array all return `success:true` but never change the persisted assignees (fresh GET is unchanged); `POST /tm/tasks/{id}/assignees` 200s but no-ops. Assignment only takes effect at **create** time (`userId` → `assignees:[userId]`, confirmed for arbitrary members). So there is no `assign`/reassign tool — set the assignee on create. **Spec update 2026-10-02:** the API now documents POST/DELETE /tm/tasks/{taskId}/assignees (15) and GET/POST/DELETE /tm/tasks/{taskId}/comments (16). Re-verify live in Phase 2; the earlier conclusions may be stale.
16. **Task comments are not exposed by the public API** — probed exhaustively (GET+POST on `/tm/tasks/{id}/comments`, `/tm/task-comments`, `/tm/comments`, `?expand=comments`, and more): all 404 or return the plain task with no comments field. A "read comments with the task" feature is impossible until WEEEK ships a comments endpoint. **Spec update 2026-10-02:** the API now documents POST/DELETE /tm/tasks/{taskId}/assignees (15) and GET/POST/DELETE /tm/tasks/{taskId}/comments (16). Re-verify live in Phase 2; the earlier conclusions may be stale.
17. **The public API *does* expose an attachment read path — under `/ws/`, not `/tm/`** — and the whole contract is readable without a token. `developers.weeek.net` is a client-rendered Zudoku SPA (every HTML path returns the same 15,619-byte shell), but it ships the full OpenAPI **3.1.1** spec to the browser as a lazy chunk: `/assets/entry.client-*.js` declares `apis: [{ input: "./apis/weeek.yaml" }]` and imports `/assets/weeek.yaml-*.js`, which `export`s the resolved `schema`. Import that chunk in Node and the spec is queryable; its `.map` also carries the pre-processed source. From it: `GET /ws/attachments/{file_id}` ("Get an attachment", tag `Attachments`, bearer) returns **JSON metadata, not bytes** — `{ success?: boolean, data: Attachment }`, with only `data` required. `Attachment` = `id`, `creatorId`, `service`, `name`, `url`, `size?`, `createdAt`; `url` is temporary ("available for an hour" when `service` is `weeek`) and `size` is present **only** for `service: weeek`. `service` is a closed set: `weeek | google_drive | dropbox | one_drive | box`, so the URL can point off-domain — hence `AttachmentsApi.download` refuses any non-`weeek` service and any URL off the API origin, and `HttpClient.download` sends no credentials at all, so the bearer token cannot reach a third party. Two earlier conclusions were wrong and are corrected here: a read path exists (the first sweep only probed `/tm/`), and the docs site is not opaque (only its HTML is). Also: `Task` carries `attachments: Attachment[]`, so ids need no scraping out of description `<img src>` markup — `toTask` now surfaces the list. Only three attachment routes exist in total: `POST /tm/tasks/{id}/attachments`, `POST /crm/deals/{id}/attachments`, `GET /ws/attachments/{file_id}` — no list, no delete.
    **Verified live 2026-10-04:** `GET /tm/tasks/{id}` really does return `attachments[]` with ids equal to the uuids in the description's `<img src>`; `GET /ws/attachments/{id}` returns `{ data: Attachment }`; the `url` is `https://api.weeek.net/ws/{wsId}/files/{uuid}?expires=…&signature=…` and needs **no bearer** — it answers `303` to a pre-signed AWS-SigV4 link on `prod-private.s3.ru-1.storage.selcloud.ru` (`X-Amz-Expires=3600`), which served the PNG (10,364 bytes, matching `size`). So the download sends no token on either hop and follows that one redirect by hand. **Environment trap:** on a VPN the storage host can resolve but be routed through the tunnel and never connect — the tool reports `could not reach <host> (UND_ERR_CONNECT_TIMEOUT) …`; `curl --interface <non-VPN interface> -L <url>` (find it with `ip route get 1.1.1.1`, the `dev` field) proves the download works off the tunnel.
18. **`TasksApi.uploadAttachment` may have been returning `[]` for every successful upload** — the spec types the upload response as `{ success, data: Attachment }` with `data` a single **object**, while the client tested `Array.isArray(j.data)` and fell back to `[]`. `TasksApi.uploadAttachment` now accepts both shapes, so the caller gets a one-element list either way. Which shape the live API actually sends is **unverified** — `files[]` is a multipart array, so a list is plausible, and this API's docs have diverged from its behaviour before (see #15, #16). One real upload settles it; until then the tolerant branch keeps both readings correct.
