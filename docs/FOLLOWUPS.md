17. **The public API *does* expose an attachment read path — under `/ws/`, not `/tm/`** — and the whole contract is readable without a token. `developers.weeek.net` is a client-rendered Zudoku SPA (every HTML path returns the same 15,619-byte shell), but it ships the full OpenAPI **3.1.1** spec to the browser as a lazy chunk: `/assets/entry.client-*.js` declares `apis: [{ input: "./apis/weeek.yaml" }]` and imports `/assets/weeek.yaml-*.js`, which `export`s the resolved `schema`. Import that chunk in Node and the spec is queryable; its `.map` also carries the pre-processed source. From it: `GET /ws/attachments/{file_id}` ("Get an attachment", tag `Attachments`, bearer) returns **JSON metadata, not bytes** — `{ success?: boolean, data: Attachment }`, with only `data` required. `Attachment` = `id`, `creatorId`, `service`, `name`, `url`, `size?`, `createdAt`; `url` is temporary ("available for an hour" when `service` is `weeek`) and `size` is present **only** for `service: weeek`. `service` is a closed set: `weeek | google_drive | dropbox | one_drive | box`, so the URL can point off-domain — hence `AttachmentsApi.download` refuses any non-`weeek` service and any URL off the API origin, and `HttpClient.download` sends no credentials at all, so the bearer token cannot reach a third party. Two earlier conclusions were wrong and are corrected here: a read path exists (the first sweep only probed `/tm/`), and the docs site is not opaque (only its HTML is). Also: `Task` carries `attachments: Attachment[]`, so ids need no scraping out of description `<img src>` markup — `toTask` now surfaces the list. Only three attachment routes exist in total: `POST /tm/tasks/{id}/attachments`, `POST /crm/deals/{id}/attachments`, `GET /ws/attachments/{file_id}` — no list, no delete.
    **Verified live 2026-10-04:** `GET /tm/tasks/{id}` really does return `attachments[]` with ids equal to the uuids in the description's `<img src>`; `GET /ws/attachments/{id}` returns `{ data: Attachment }`; the `url` is `https://api.weeek.net/ws/{wsId}/files/{uuid}?expires=…&signature=…` and needs **no bearer** — it answers `303` to a pre-signed AWS-SigV4 link on `prod-private.s3.ru-1.storage.selcloud.ru` (`X-Amz-Expires=3600`), which served the PNG (10,364 bytes, matching `size`). So the download sends no token on either hop and follows that one redirect by hand. **Environment trap:** on a VPN the storage host can resolve but be routed through the tunnel and never connect — the tool reports `could not reach <host> (UND_ERR_CONNECT_TIMEOUT) …`; `curl --interface <non-VPN interface> -L <url>` (find it with `ip route get 1.1.1.1`, the `dev` field) proves the download works off the tunnel.

    - **Deals** — `weeek_update_deal` uses `DealsApi.replace` (PUT) for title, amount, outcome and `fields`; `assignees`, `organizations`, `contacts` and `tags` are applied as a diff through the add/remove routes; `description` leaves the update schema (create-only); `toDeal` reads tags as integers or `{ id }` objects; `dealSorts` loses `amount`; the deal lookup's fall-through message names the id that matched nothing.
    - **Organizations** — `weeek_create_organization`/`weeek_update_organization` take one `responsible` (member by name or id, null clears) sent as `responsibleId`; `NewOrganization`/`OrganizationUpdate` drop `responsibles`.
    - **Verification** — both smoke scripts re-run on the fixed local build before the tag; the harness and scripts live in `.superpowers/smoke/` (git-ignored).
